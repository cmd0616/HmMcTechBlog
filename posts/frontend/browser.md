> 浏览器是前端工程师最熟悉的"黑盒"。输入一个 URL 到页面可以交互，背后发生了什么？点击一次鼠标，浏览器又如何知道我们点的是哪个元素？本文沿着"渲染流程"和"事件处理"两条主线，把这两个经典问题讲清楚。

## 一、浏览器是如何渲染界面的

1. 解析 HTML，生成 DOM 树
浏览器把 HTML 文本解析成节点，形成 DOM 树，表示页面结构。

2. 解析 CSS，生成 CSSOM 树
CSS 会被解析成样式规则树。CSS 是渲染阻塞的，浏览器通常需要拿到并计算完样式后，才能确定元素长什么样。

3. 生成渲染树
DOM + CSSOM 合并成渲染树。不可见元素（比如 display: none）通常不会进入渲染树，但 visibility: hidden 会保留。

4. 布局 / 重排
浏览器计算每个可见元素的位置、宽高、层级关系。改动 width、height、margin、padding、字体大小、窗口缩放等，可能触发重排。

5. 绘制
把元素的颜色、边框、阴影、文字、背景等转换成绘制指令，生成位图或图层。

6. 光栅化
图层会被拆成小块，交给 GPU 或渲染线程转成实际像素。

7. 合成
合成线程把各图层按顺序组合，再交给 GPU 显示。transform、opacity 这类属性更容易只触发合成阶段，所以做动画时通常更流畅。

## 二、浏览器如何捕捉点击事件

1. 操作系统把点击交给浏览器
用户点击鼠标或触摸屏幕后，操作系统先收到输入信号，再交给浏览器进程。

2. 浏览器进程把事件转发给渲染进程
浏览器进程知道"某个标签页在某个坐标发生了点击"，但具体点中了哪个元素，要交给渲染进程处理。

3. 合成器线程先判断是否需要主线程参与
渲染进程里的合成器线程会检查点击区域是否绑定了事件处理器。如果页面某些区域被标记为"非快速滚动区域"，合成器线程会把事件发给主线程处理；否则合成器线程可能直接合成帧，不必等待主线程。

4. 主线程做命中测试
主线程根据点击坐标 (x, y)，结合布局信息、z-index、透明度、pointer-events 等，判断到底点中了哪个元素。这个元素就是 event.target。

5. 生成事件对象并入队
浏览器会创建一个 MouseEvent，里面包含点击类型、目标元素、坐标等信息，然后把它放进事件队列。

6. 事件循环调度执行
   当 JS 主线程空闲时，事件循环从队列取出事件，分发到对应元素上注册的监听器。如果主线程正在执行耗时任务，点击事件会先排队，等主线程空闲后才执行。

   事件循环把事件分发到监听器，本质上就是按顺序调用开发者绑定的回调函数。按 DOM 事件流依次调用路径上所有匹配的监听器。

7. 事件沿 DOM 树传播
   事件会经历三个阶段：

   - 捕获阶段：从 window / document 向下传播到目标元素；
   - 目标阶段：在目标元素上触发；
   - 冒泡阶段：从目标元素向上传播到祖先元素。

**小结**：前四步解决"点的是谁"的问题，依赖渲染流程产出的布局信息（也就是 HTML/CSS 的成果）；后三步进入 JS 世界，负责创建事件对象、调度回调、按 DOM 事件流通知监听者。一次点击从硬件到我们的回调函数，就这样跨过了进程、线程和事件循环。

## 三、下一篇预告

这篇我们沿着两条主线各走了一遍，但每一步背后还有更深的机制没有展开。下面这些问题，留到下一篇文章细说：

**渲染篇：**

- 浏览器是如何进行上述操作的？浏览器为什么具有这些能力？
- 浏览器和 GPU 是怎么交互的？

**事件篇：**

- 操作系统如何识别到点击事件的，又是怎么交给浏览器的？
- 浏览器是如何将事件转发给渲染进程的？浏览器为什么具有这个能力？
- 主线程为什么要做命中测试？具体是如何做的？
- 为什么要生成事件对象？又是如何生成的？
- DOM 事件流是什么？具体作用是什么？
- 事件的传递为什么是这三个阶段？

## 总结

渲染流程回答"页面长什么样"：HTML/CSS 决定结构与样式，经过布局、绘制、光栅化、合成，最终由 GPU 输出像素；点击事件回答"交互怎么被响应"：操作系统投递输入，浏览器进程转发，渲染进程定位目标，最后由事件循环调度 JS 回调。

两条线串联起来，就是一次"显示 + 交互"的完整闭环。理解这两条链路，也是理解性能优化的根基：减少重排重绘、把动画交给合成层、用事件委托降低监听器数量——所有手段，优化的都是这条链路上的某个环节。
