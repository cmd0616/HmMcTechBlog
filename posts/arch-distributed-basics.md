## 先说结论：微服务不是银弹

> 「单体失败的原因，往往是组织问题，而不是技术问题。」—— 参见康威定律

## 单体架构并不丢人

一个 10 人团队维护的模块化单体（Modular Monolith），部署简单、调试方便、事务一致，
**绝大多数业务规模下它是正确答案**。

## 什么时候该拆分

| 信号 | 说明 |
|------|------|
| 团队规模 > 40 人 | 代码合并冲突频发，发布互相阻塞 |
| 局部扩容需求 | 只有订单模块需要扛大促流量 |
| 技术栈诉求 | 算法模块需要 Python，其余是 Java |
| 故障隔离 | 一个模块 OOM 拖垮整个进程 |

## 拆分的正确姿势

### 1. 按「业务能力」拆，而不是按技术层拆

```
（错误示范）user-service / db-service / util-service
（正确姿势）order-service / inventory-service / payment-service
```

### 2. 先模块化，再服务化

单体内部先用模块边界 + 独立数据库 Schema 练手，边界稳定后再物理拆分。

### 3. 分布式带来的新账单

- **网络不可靠**：超时、重试、幂等设计
- **数据一致性**：Saga、最终一致性、事件驱动
- **可观测性**：链路追踪（OpenTelemetry）从可选变成必需
- **运维成本**：CI/CD、服务网格、配置中心……

## 一个务实的演进路径

```
单体 → 模块化单体 → 抽离 1~2 个高负载服务 → 按需继续拆分
```

## 小结

架构决策的本质是**权衡**（trade-off）。能解决问题的最简架构，就是最好的架构。
